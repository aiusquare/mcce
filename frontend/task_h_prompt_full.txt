# TASK H: Fix Incorrect Carryover Classification in the First Entry Cohort Result Sheets

## Project

MCCE Academic Management System

Backend repository: https://github.com/aiusquare/mcce-backend

Frontend: React/TypeScript, local project

Backend: CodeIgniter 3, PHP, MySQL

Local test database: mcce_test

Existing academic database: mcceorgn_main

## Confirmed academic rules

The institution's first admission cohort was 2021/2022.

In 2021/2022:

- Fresh students started in Contact 1.
- Direct Entry students started in Contact 2.

The EAP programme admitted 146 Direct Entry students.

The GST111 result batch for 2021/2022 Contact 2 currently displays 146 DE students, with 117 classified as regular and 29 as carryover.

This classification is suspicious because these were the students' first examinations in their programme.

Carryover corrections should be recorded in later eligible academic periods following an actual previous failed attempt.

## Phase 1: Perform database forensics before changing code

Read the relevant controllers, models and frontend components.

Locate the exact 2021/2022 Contact 2 GST111 EAP result batch.

Use read-only SQL to inspect:

- All 146 students.
- Their entry modes.
- Their entry cohorts.
- Their original result attempts.
- Stored registration_type_snapshot values.
- Returned backend is_carryover values.
- Associated registration headers and items.
- Original and later academic session IDs.
- Provenance and correction relationships.

Identify the exact 29 students classified as carryover in the current UI.

For each student, determine whether the label originated from:

A. A wrongly matched later registration.

B. An incorrectly stored registration_type_snapshot.

C. A falsely inferred earlier failed attempt.

D. An incorrect or fabricated source_result_attempt_id.

E. Frontend classification overriding the original attempt type.

F. A combination of these problems.

Report the actual count under each category.

Do not assume all 29 have the same cause.

Do not change the academic database during this audit.

## Phase 2: Correct the class-list session leak

Inspect:

application/controllers/Admin_course_registration.php

Method:

get_class_list()

The existing query contains logic equivalent to:

```php
$this->db->where_in('r.session_id', $target_session_ids);
$this->db->or_where_in('s.session_name', $target_session_ids);
```

This can admit registrations from later academic sessions because the student's entry cohort matches the requested historical session.

Remove the entry-cohort condition from teaching-session registration eligibility.

Use the canonical course_registrations.academic_session_id when populated.

Use legacy session_id only when the canonical academic-session field is missing or empty.

Resolve UUID and textual session representations consistently.

Entry-cohort fields must remain available for cohort filtering and display, but must never broaden the teaching-session population query.

Preserve legitimate carryovers registered in the correct later academic period.

## Phase 3: Correct outstanding-course detection

Inspect:

application/models/Outstanding_course_model.php

Pay particular attention to:

- get_outstanding_students_for_course_before()
- get_outstanding_students_for_courses_before()
- get_outstanding_courses_before()
- is_before()

An actual carryover requires a verified prior failed examination.

Validate that the source attempt:

1. Belongs to the same student.
2. Belongs to the same course.
3. Occurred strictly before the target examination period.
4. Belongs to the student's legitimate academic history.
5. Was not already cleared by a subsequent successful correction.
6. Is linked through valid registration and provenance evidence.

Do not allow a later registration to validate an unrelated historical result attempt.

Resolve Direct Entry mode from the authoritative student/admission records, including admissions.mode_of_entry where applicable.

For the 2021/2022 DE entrants, Contact 2 was their first programme contact.

A Contact 1 record from that same session must not be interpreted as an ordinary previous failed examination for these students.

Do not create false Contact 1 examination histories for DE students.

Preserve valid transfers or officially recognised exceptions only when supported by explicit academic records and policy.

Do not classify a student as a carryover merely because their course was previously associated with another contact or the registration item contains the word carryover.

## Phase 4: Correct result-attempt classification

Inspect:

application/models/Results_model.php

Methods:

- get_registered_students_for_batch()
- populate_batch_attempts()
- get_attempts_by_batch()
- save_attempts()

For each historical batch, distinguish:

- Curriculum course type.
- Current-period registration type.
- Stored examination-attempt type.
- Verified carryover status.

A result attempt must be classified as carryover only when supported by valid historical evidence for that specific attempt.

Do not allow later changes in registration status to retrospectively reclassify the student's first examination.

Do not overwrite stored examination snapshots in GET requests.

Do not trust a frontend-submitted is_carryover flag without server-side validation.

Ensure that save_attempts rejects an invalid carryover source without changing a valid regular result.

Preserve the existing Fix D provenance protections.

## Phase 5: Correct the React frontend

Inspect the latest local equivalent of:

frontend/src/components/admin/results/ResultBatchDetail.tsx

frontend/src/lib/resultBatchAttempts.ts

The frontend currently combines multiple carryover indicators using OR conditions.

This can allow an incorrectly matched class-list record to override the classification of a valid first examination attempt.

Use the backend's verified per-attempt classification as the authoritative display value.

Do not infer carryover merely because:

- The student has a previous result somewhere.
- A class-list row was marked carryover.
- A registration exists in another academic session.
- The stored snapshot conflicts with a verified current classification.

Treat unresolved classification conflicts as integrity warnings.

Ensure the frontend uses the batch's canonical academic_session_id for class-list requests, with the documented legacy fallback.

Only generate pending carryover rows when the backend verifies eligibility for the requested session and course.

Do not delete or hide historically scored attempts merely because their old registration link is incomplete.

Do not submit a carryover flag derived from unverified frontend data.
